# HTML plans

Use this for plans, roadmaps, implementation sequences, and rollout documents whose source commitments should remain easy to inspect.

Read the brief and source plan first. Preserve scope, ordering, commitments, and terminology unless asked to synthesize more broadly. Improve clarity without turning a task plan into a strategy document.

Include only fields supported by the source, such as:

- phases, sequence, or decision points;
- owners and collaborators;
- dependencies and risks;
- acceptance checks and unresolved questions.

Separate accepted decisions from assumptions and open questions. Show dependencies and order only when real. Use tables for exact mappings and repeated fields; use a timeline or flow only when it improves understanding. Keep prose readable rather than forcing every paragraph into cards.

Verify that no commitment disappeared, sequence is preserved, ownership and dependencies are clear, and long content works at narrow widths. Note any structural interpretation introduced.
